# Events and states reference

Lookup tables for the case types, states and events that `sptribs-case-api` declares through the ccd-config-generator SDK. For how the states fit together, with a state diagram, see [case-lifecycle.md](case-lifecycle.md).

In summary:

- On master there is one case type: `CriminalInjuriesCompensation` in jurisdiction `ST_CIC`.
- It has 21 states, from the [`State`](../src/main/java/uk/gov/hmcts/sptribs/ciccase/model/State.java) enum. Ten of them are not set as a to-state by any event in the normal lifecycle.
- Caseworker, common and citizen event IDs are constants in [`EventConstants`](../src/main/java/uk/gov/hmcts/sptribs/caseworker/util/EventConstants.java), except `create-test-case`, whose constant is in `CreateTestCase`. Three citizen events read their IDs from `caseinfo.apps[].eventIds` in `application.yaml`, which hold the same values. Each system event declares its ID as a constant in its own class.
- There are 66 event classes: 45 in `caseworker/event/`, 4 in `common/event/`, 4 in `citizen/event/` and 13 in `systemupdate/event/`.
- CCD rejects an event if the case is not in one of its declared from-states. Many events set the new state in their `aboutToSubmit` response instead of in the event config.

## CIC states

The State ID column is the CCD ID. The config generator uses the enum constant name as the ID (`StateGenerator` calls `toString()`, which `State` does not override), so the DSS IDs are `DSS_Draft`, `DSS_Expired` and `DSS_Submitted`; the hyphenated strings such as `DSS-Draft` are the `@CCD` `label` (display name). Every state has the hint `### ${cicCaseFullName}` followed by `Case number: ${hyphenatedCaseRef}`.

| State ID | Display name | Meaning |
|---|---|---|
| `DSS_Draft` | DSS-Draft | Citizen draft created by the DSS journey (`citizen-cic-create-dss-application`). Pre-submission. |
| `DSS_Expired` | DSS-Expired | A DSS draft with no change for 30 days or more. `system-clear-inactive-dss-draft-case` moves cases here. The citizen cannot submit from it. |
| `DSS_Submitted` | DSS-Submitted | The citizen has submitted the DSS application. A caseworker's first `edit-case` moves it to `Submitted`. |
| `Draft` | Draft | Legacy. The create events declare it as `initialState`, but each one's `aboutToSubmit` returns a different state. Only `create-test-case` can leave a case here. Carries `SolicitorAccess`. |
| `Submitted` | Submitted | Formally submitted and visible to caseworkers. Reached from `DSS_Submitted` by `edit-case`, or directly by `caseworker-create-case` and `system-create-test-case`. |
| `NewCaseReceived` | New case received | Not set by any event on master. Listed as a from-state by the document-management and contact-parties events. |
| `CaseManagement` | Case management | Caseworkers prepare the case: bundle, panel, orders and hearing details. |
| `ReadyToList` | Ready to list | Hearing options are recorded and the case can be listed. `caseworker-hearing-options` moves cases here. |
| `AwaitingHearing` | Awaiting hearing | A hearing is listed (`caseworker-record-listing`). |
| `AwaitingOutcome` | Awaiting outcome | The hearing summary is recorded (`create-hearing-summary`) and the decision is awaited. |
| `CaseStayed` | Case stayed | On hold. Entered with `caseworker-stay-the-case` and left with `caseworker-remove-stay`. |
| `CaseClosed` | Case closed | Closed by `caseworker-close-the-case`, `caseworker-issue-final-decision`, or `caseworker-issue-decision` with a Rule 27 or strike-out template. `caseworker-reinstate-state` moves it back to `CaseManagement`. |
| `StrikeOut` | Case Strike Out | Not set by any event on master. Closing for this reason lands in `CaseClosed`. |
| `ConsentOrder` | Consent Order | Not set by any event on master. Closing for this reason lands in `CaseClosed`. |
| `Rule27` | Rule 27 | Not set by any event on master. Closing for this reason lands in `CaseClosed`. |
| `Concession` | Case Concession | Not set by any event on master. Closing for this reason lands in `CaseClosed`. |
| `DeathOfAppellant` | Death of Appellant | Not set by any event on master. Closing for this reason lands in `CaseClosed`. |
| `Completed` | Application completed | Not set by any event on master. A final decision closes the case into `CaseClosed`. |
| `Withdrawn` | Application withdrawn | Not set by any event on master. Closing for this reason lands in `CaseClosed`. |
| `Rejected` | Application rejected | Not set by any event on master. Closing for this reason lands in `CaseClosed`. |
| `Sent` | Application Sent | Not set by any event on master, and no event lists it as a from-state. |

The ten states marked "not set by any event" are not reached in the normal lifecycle. `create-test-case` can set any of them, for test data.

## How to read the event tables

- **From-states** come from `forStates(...)`, `forState(...)`, `forStateTransition(from, to)`, `forAllStates()` or `initialState(...)`. "none (creates the case)" means the event uses `initialState` and starts a new case.
- **To-state** is the state the event leaves the case in. "(callback)" means the `aboutToSubmit` response sets it. "unchanged" means neither the config nor a callback changes the state.
- **Roles granted**: `CRU`, `CRUD` and the like are the `Permissions` sets passed to `grant(...)`. "History" lists the roles passed to `grantHistoryOnly(...)`, which can see the event in case history but cannot trigger it unless also granted CRU.
- **Callbacks** are the event-level `aboutToStart`, `aboutToSubmit` and `submitted` callbacks. Mid-event callbacks on individual pages are not listed.
- Role names are `UserRole` constants. `ST_CIC_WA_CONFIG_USER` is `caseworker-wa-task-configuration`.
